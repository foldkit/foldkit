# Agent Development Notes

This is a Foldkit app. Read [`FOLDKIT.md`](./FOLDKIT.md) before writing any code in this project. It covers the architecture, the APIs, and the conventions the project is built on.

A root uses one of two complete layouts. A genuinely compact root keeps Model, Message, init, update, view, `Application`, `ApplicationComposition`, and any small local handler bundle together in `application.ts`. Once any root responsibility is extracted, split the whole root: `definition.ts` owns `Application`; `model.ts`, `message.ts`, `init.ts`, `update.ts`, `view.ts`, and optional `flags.ts` own their named responsibilities; and `composition.ts` or `composition/composition.ts` owns Bindings, OutMessage folds, complete child/Mount registration, `ApplicationComposition`, and an optional `ApplicationViewBuilder`. Even a graphless split root has `composition.ts`. Remove the emptied `application.ts` instead of using it as a forwarding barrel. A simple root `EffectsLayer` stays with its Command definitions in `command.ts`; use `layer.ts` only for substantial or reused Layer composition. Composition imports the Definition and child or Mount definitions, never root init, update, or view. Import `defineApplication` from `foldkit`; create every root Composition with `Application.makeComposition(...)`, even when it has no child Bindings or Mounts. Author init, update and the primary view through that named Composition, then pass them explicitly to `ApplicationComposition.makeApplication(...)` or `ApplicationComposition.makeElement(...)`. A split feature uses composition.ts, including for Mount-only registrations. Shared Mount definitions live in mount.ts. Parent-owned Bindings from Application.bindChild(...) are passive relationship configuration; including them in the Composition's `childBindings` registers them. `entry.ts` imports each implementation piece from its real owner, lists those fields explicitly in completion, owns the browser container and startup inputs, calls `application.provide(ApplicationLayer)` when needed, and starts the Runtime. Keep root `ApplicationLayer` composition in `services.ts`. Tests and server entries import the passive Composition and the pieces they need without starting the browser Runtime. Name the root Route union `ApplicationRoute` and the root provider `ApplicationLayer` (`ApplicationTestLayer` for its test alternative).

## Project Notes

Domain vocabulary, deployment steps, local conventions that differ from Foldkit's defaults: write them here.

For a required direct child field, omit `init` when its initializer accepts no arguments; use `init: { args }` for required inputs or `init: false` when the parent supplies that field. Optional, keyed, and accessor storage remains parent-owned when `init` is omitted; explicit `init.args`, keyed `init.occurrences` / `init.toItem`, or a checked custom projection chooses automatic startup. An optional `Startup` Schema on the parent Definition contextually types selectors that share startup input. Author root startup through `ApplicationComposition.makeInit`, returning parent-owned `model` fields plus optional ephemeral `startup`, parent `commands`, and post-assembly `steps`. Composition initializes and places child Models and collects their Commands. Use `ApplicationComposition.makeUpdate` for parent transitions; ordinary registered wrappers route automatically, while keyed/contextual policies belong on Binding `fromParentMessage`. See FOLDKIT.md for optional presence, exact keyed identity and startup Steps.
