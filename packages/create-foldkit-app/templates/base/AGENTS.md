# Agent Development Notes

This is a Foldkit app. Read [`FOLDKIT.md`](./FOLDKIT.md) before writing any code in this project. It covers the architecture, the APIs, and the conventions the project is built on.

A compact root keeps its contracts, Composition, portable builders and selected `ApplicationBlock` in `application.ts`. Once a structural responsibility is extracted, use the complete split layout: `definition.ts` establishes the stable unique key, Model, local Message, Init tuple, optional Context/OutMessage/ChildInitContext and view/operation/effect contracts; `composition.ts` owns static Bindings, OutMessage policy, child/Mount registration and `ApplicationComposition`; named init/update/view/command files own their implementation; and `block.ts` completes `ApplicationDefinition.makeBlock(Effect.gen(...))`. Yield each registered Binding there, return the acquired connections under `children`, and provide the child construction Layers. A graphless root returns `children: []`.

A child feature exports `FooBlock = FooDefinition.contract` separately from its implementation `layer`. Composition and extracted builders import child contracts; only completion imports child implementation Layers. The root exports the selected `ApplicationBlock` for Program/Server hosting. `entry.ts` chooses the host, container and startup inputs, supplies ordinary Services through `program.provide(ApplicationLayer)`, and starts Runtime. Imported Definition, Composition and Layer recipes stay passive. Child startup selectors remain deferred until parent init, handler dependencies remain in their handler constructors, and application state stays in the Model.

Split implementations named-import their needed Step helpers from `definition.ts`; compact implementations destructure them beside the Definition. Keep Definition qualification where several owners share one module. Keep shared Mount definitions in `mount.ts` and substantial local handler Layer composition in `layer.ts`; feature barrels do not reexport authoring helpers. Remove an emptied `application.ts` and use an explicit `index.ts` barrel. Name the root Route union `ApplicationRoute`, ordinary Service provider `ApplicationLayer`, and its test alternative `ApplicationTestLayer`.

Block-aware Story and Scene runners return scoped Effects. Use their `init(...args)` step to preserve init Model and Commands, `given(model)` for a deliberate prebuilt state, and normal Layer provision for implementation construction. Their ordinary steps stay synchronous and do not run handlers. See FOLDKIT.md for exact view/context/routing and deferred child-message testing forms.

Name application-authored Step values and factories for their operation: `clearSearch`, `changeSearchQuery(query)`, and `applyDomainResult(result)`. Their definitions and types establish the Step role; omit the `make` prefix and `Step` suffix from these application names. Preserve framework helpers and types such as `makeStep`, `makeFieldsStep`, `makeCommandsStep`, `makeOutMessageStep`, `makeNoopStep`, `Update.Step`, and `Update.combineSteps`, along with other public framework helpers whose names include `Step`. Keep existing naming conventions for unrelated factories, Commands, Messages, Bindings, OutMessage folds and matchers, dedicated `handle<MessageTag>` handlers, public operation keys, and applied update-like results.

Keep a Step used by only one responsibility with that code. Put reusable Steps shared by update, composition, or init in the owning Block's `steps.ts`. For a larger module, use responsibility files such as `steps/search.ts` and `steps/quoteLoading.ts`, with an explicit `steps/index.ts` barrel. The owner is the Block whose Model the Step transforms. Keep shared Steps independent of the owning update and completed Block.

`update.ts` maps incoming Messages to handlers and Steps. `composition.ts` registers relationships and maps child OutMessages to parent Steps. `steps.ts` owns the reusable transitions those entry points share. Keep Binding registration and OutMessage policy in composition. Name shared transitions for their operation, without a `make` prefix or `Step` suffix. A Step that closes over a Binding from composition must read it in a deferred producer when the modules depend on one another; module initialization must not invoke that Binding.

## Project Notes

Domain vocabulary, deployment steps, local conventions that differ from Foldkit's defaults: write them here.

For a required direct child field, omit `init` when its initializer accepts no arguments; use `init: { contextToArgs }` for required inputs or `init: false` when the parent supplies that field. Optional, keyed, and accessor storage remains parent-owned when `init` is omitted; explicit `init.contextToArgs`, keyed `init.instances` / `init.toItem`, or a checked custom projection chooses automatic startup. An optional `ChildInitContext` Schema on the parent Definition contextually types selectors that prepare arguments for direct child initializers. Author root startup through `ApplicationComposition.makeInit`, returning parent-owned `model` fields plus optional ephemeral `childInitContext`, parent `commands`, and post-assembly `steps`. Composition initializes and places child Models and collects their Commands. Use an exhaustive `ApplicationComposition.makeUpdate` handler record for parent transitions; registered Bindings route generated child envelopes before local handlers. Use `makeUpdate({})` when the parent has no locally authored Messages and `.withContext` when handlers need dispatch context. Put delivery admission in `delivery.when`, derive required child update context with `delivery.toUpdateContext`, and provide `keySchema` for a custom keyed Binding. See FOLDKIT.md for optional presence, exact keyed identity and startup Steps.
