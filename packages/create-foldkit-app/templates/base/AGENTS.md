# Agent Development Notes

This is a Foldkit app. Read [`FOLDKIT.md`](./FOLDKIT.md) before writing any code in this project. It covers the architecture, the APIs, and the conventions the project is built on.

A compact feature may keep its complete implementation together. A split feature declares `FooBlock`, its adjacent key and needed authoring helpers in `block.ts`; `composition.ts` owns static Bindings, OutMessage policies and graph-aware builders; `layer.ts` completes `FooBlock.makeLayer({ init, update, view, ... })` and provides child implementation Layers. The record acquires the init plan's registered child inventory when its Layer is built; use plans from that same Composition. Keep a custom Effect constructor for genuine construction dependencies or scoped work, with explicit acquired `children`. Put a separate local handler bundle in `effectsLayer.ts`. Ordinary Services remain in `services.ts` or a feature-owned provider. Keep init, update, view, Commands and lifecycle definitions in their responsibility modules. Never use `layer.ts` for the local EffectsLayer bundle. A compact root keeps all structural pieces in `block.ts`; retain its declaration when splitting. The root entry selects `{ block: ApplicationBlock, layer }` and starts the Runtime.

A child feature exports `FooBlock = Block.make(...)` separately from its implementation `layer`. Composition and extracted builders import child contracts; only completion imports child implementation Layers. The root exports the `ApplicationBlock` and its construction `layer` for Program/Server hosting. `entry.ts` chooses the host, container and startup inputs, supplies ordinary Services through `program.provide(ApplicationLayer)`, and starts Runtime. Imported Block declarations, Compositions and Layer recipes stay passive. Child startup selectors remain deferred until parent init, handler dependencies remain in their handler constructors, and application state stays in the Model.

Split implementations named-import their needed Step helpers from `block.ts`; compact implementations destructure them beside the Block declaration. Keep Block qualification where several owners share one module. Keep shared Mount definitions in `mount.ts` and separate local handler bundles in `effectsLayer.ts`; feature barrels do not reexport authoring helpers. Keep the declaration in `block.ts` when splitting, and use an explicit `index.ts` barrel. Name the root Route union `ApplicationRoute`, ordinary Service provider `ApplicationLayer`, and its test alternative `ApplicationTestLayer`.

Block-aware Story and Scene runners return scoped Effects. Use their `init(...args)` step to preserve init Model and Commands, `given(model)` for a deliberate prebuilt state, and the paired `{ block: FeatureBlock, layer }` for implementation construction. Their ordinary steps stay synchronous and do not run handlers. See FOLDKIT.md for exact view/context/routing and deferred child-message testing forms.

Name application-authored Step values and factories for their operation: `clearSearch`, `changeSearchQuery(query)`, and `applyDomainResult(result)`. Their definitions and types establish the Step role; omit the `make` prefix and `Step` suffix from these application names. Preserve framework helpers and types such as `makeStep`, `makeFieldsStep`, `makeCommandsStep`, `makeOutMessageStep`, `makeNoopStep`, `Update.Step`, and `Update.combineSteps`, along with other public framework helpers whose names include `Step`. Keep existing naming conventions for unrelated factories, Commands, Messages, Bindings, OutMessage folds and matchers, dedicated `handle<MessageTag>` handlers, public operation keys, and applied update-like results.

Keep a Step used by only one responsibility with that code. Put reusable Steps shared by update, composition, or init in the owning Block's `steps.ts`. For a larger module, use responsibility files such as `steps/search.ts` and `steps/quoteLoading.ts`, with an explicit `steps/index.ts` barrel. The owner is the Block whose Model the Step transforms. Keep shared Steps independent of the owning update and completed Block.

`update.ts` maps incoming Messages to handlers and Steps. `composition.ts` registers relationships and maps child OutMessages to parent Steps. `steps.ts` owns the reusable transitions those entry points share. Keep Binding registration and OutMessage policy in composition. Name shared transitions for their operation, without a `make` prefix or `Step` suffix. A Step that closes over a Binding from composition must read it in a deferred producer when the modules depend on one another; module initialization must not invoke that Binding.

Declare the unique key immediately before its Block and give `Symbol('Feature')` the same description as the Block's readable name. Keep the key private unless verified declaration emission needs its original declaration exported. Split implementation modules commonly need that export because their inferred contracts name the owner key. A public barrel may re-export the original declaration with `export type` when only its identity is needed in types. Verify source and relocated declarations before removing an export.

Declare parent requests and notifications in the child's `InMessage` union and handle them with `Composition.makeInMessageUpdate`. `RequestedX` generates `Binding.requestX`, and `InformedOfX` generates `Binding.informOfX`. The remaining suffix is preserved exactly; other prefixes and empty suffixes are rejected. Methods take the constructor payload when present, with a keyed occurrence first and InMessage context last. They return connected parent Steps, so pass them directly to handler records or compose them. Do not add a manual request wrapper or an `operations` entry that only repeats an InMessage constructor. Keep explicit operations for real argument adaptation, generic interfaces or intentional local-Message mappings.

Application behavior belongs in Story or Scene. Use their DSL to deliver Messages and InMessages, resolve Commands, and assert Models, OutMessages and views. Do not manually chain acquired `update` calls or invoke application Steps as a substitute for the DSL. Pure fixture construction and intentional `given(model)` remain valid; use scoped acquisition only when a fixture genuinely needs initialized state, graph identity or custom view context. Keep pure domain/selector tests separate from application behavior, and reserve low-level transition tests for framework infrastructure. Keep Story and Scene specifications declarative: use immutable fixtures, `messageWith` for a value read from the current Model, and observable assertions. Do not carry values between steps through mutable outer captures or `mockImplementation` closures; establish a genuine DSL gap before introducing a mutable bridge.

## Project Notes

Domain vocabulary, deployment steps, local conventions that differ from Foldkit's defaults: write them here.

For a required direct child field, omit `init` when its initializer accepts no arguments; use `init: { contextToArgs }` for required inputs or `init: false` when the parent supplies that field. Optional, keyed, and accessor storage remains parent-owned when `init` is omitted; explicit `init.contextToArgs`, keyed `init.instances` / `init.toItem`, or a checked custom projection chooses automatic startup. An optional `ChildInitContext` Schema on the parent Block contextually types selectors that prepare arguments for direct child initializers. Author root startup through `ApplicationComposition.makeInit`, returning parent-owned `model` fields plus optional ephemeral `childInitContext`, parent `commands`, and post-assembly `steps`. Composition initializes and places child Models and collects their Commands. Use an exhaustive `ApplicationComposition.makeUpdate` handler record for parent transitions; registered Bindings route generated child envelopes before local handlers. Use `makeUpdate({})` when the parent has no locally authored Messages and `.withContext` when handlers need dispatch context. Put delivery admission in `delivery.when`, derive required child update context with `delivery.toUpdateContext`, and provide `keySchema` for a custom keyed Binding. See FOLDKIT.md for optional presence, exact keyed identity and startup Steps.
