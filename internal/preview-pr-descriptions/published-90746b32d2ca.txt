## Changes since the previous preview

The previous preview is `f3be22cfeefed437164ad614d08b16d9000e0703`. It already includes checked Block assembly, record-only `makeUpdate`, focused Step producer callbacks, aggregate ManagedResource Layers, and the contributor work credited in that snapshot. Keep those APIs and the existing child graph.

### Required migrations

- Replace standalone `makeMapBinding` calls with the parent Definition's `makeMapBinding` method. The `foldkit/mapBinding` import is removed. Applications without map Bindings need no change for this migration.
- Rename generic UI Block factories to `makeBlock`: Listbox, Combobox, Menu, RadioGroup, Tabs, and VirtualList replace `create`, including the Listbox and Combobox Multi variants; Toast replaces `make`. The old names have no compatibility aliases.
- If the application uses experimental Machine, replace curried `Machine.define` and standalone authoring helpers with `Machine.makeDefinition`, its bound `makeGuard`, `makeHandler`, and `makeTransitions` helpers, and `Definition.makeMachine`.
- Migrate persisted experimental Query Models for the new freshness and recency metadata. Existing Query behavior defaults remain unchanged when Models are not persisted.
- Update exhaustive VirtualList parent policies for the new `ApproachedLoadedStart` and `EndedContainerScroll` OutMessages.

See the [previous-preview upgrade guide](https://foldkit-website-preview-pu7rp0p5a-devin-jamesons-projects.vercel.app/preview-upgrade) for exact before-and-after forms and verification steps.

### Authoring and lifecycle fixes

- Inline Model-aware `makeStep` handlers, including `.withContext`, infer their exact Message variants. Contextual update records accept compatible Steps and Binding operations directly. Registration-evidence extraction also avoids TS2589 in the reported large Root composition while preserving registration checks.
- Scene follows renderer element identity for Mount lifetimes, and Runtime releases an element's original Mount when that element is removed after dropping `OnMount`. Scene also adds explicit URL-change delivery and `Scene.unhover`.
- Subscription entries accept Model-based `when` gates, with explicit Scene activity assertions. Handler constructors still run at Runtime startup and retain their Service requirements and errors.
- SSR development reloads recreate Block Definitions with their declarations, and server entries can register an HMR disposal callback. SSG preview resolves prerendered extensionless routes without reexecuting the server entry.
- Effect peers accept the verified 4.0.0 and 4.0.6 pairs while application and development pins remain exact.

### Machine, Query, and VirtualList additions

- [Machine](https://foldkit-website-preview-pu7rp0p5a-devin-jamesons-projects.vercel.app/core/machine) binds its State, Message, and optional Context Schemas once, checks completed transition tables, preserves exact handler narrowing and Command requirements, and retains pure transition, folding, and graph analysis.
- [Query and KeyedQuery](https://foldkit-website-preview-pu7rp0p5a-devin-jamesons-projects.vercel.app/core/query) add freshness-aware loading, targeted cancellation, accepted-completion OutMessages, bounded settled retention, and pending-request inspection. Pending entries are protected from eviction and can temporarily exceed the settled-entry limit.
- [VirtualList](https://foldkit-website-preview-pu7rp0p5a-devin-jamesons-projects.vercel.app/ui/virtual-list) adds continuous upward history, semantic table rows, ancestor and Window scroll ownership, and positioned ordinary rows. Parent Blocks continue to own fetching, loaded rows, table structure, and external layout.

Additional opt-in helpers include `makeInitIfMissingStep`, `Route.parsePathWithFallback`, and `makeStep.fromMessage`. Active examples, scaffolds, docs, and skills use adjacent Schema type aliases as an authoring convention; this is not a consumer API migration.

## Why Foldkit is making this change

**Build applications from Blocks. Fold their updates into a single application Model.**

Blocks give features ownership of their state, behavior, optional views, effects, and public operations. A counter and a large website follow the same architecture.

Parents connect Blocks through Bindings. Foldkit handles repetitive child initialization, Message routing, and lifecycle wiring. You decide which children exist, how they coordinate, and what your application does. TypeScript checks those connections and dependencies as the application is assembled.

**This is a breaking release combining Block composition and handler Layers.**

## What changes

### 1. Reusable features become checked Blocks

A feature exports a completed value such as `SearchBlock`. Parents use its Model Schema, connect it through a Binding, and use the Binding's operations and view. The feature's implementation stays internal.

Authoring has three stages:

1. **Definition** establishes identity, contracts, and early authoring helpers.
2. **Composition** registers children and Mounts and authors init, update, and view.
3. **Assembly** prepares a checked draft through `Composition.prepareBlock`, then exports the completed Block through `Block.assemble(prepare)` with its checked `FromAssembly*` annotation. The explicit Model/producer boundary keeps parent Schema access from demanding full implementation inference.

These stages build configuration. Runtime constructs Layers and executes effects later. Even a feature without children or Mounts uses a Composition.

Preparation requires each handler to be supplied locally or delegated through `hostHandlers`. Delegated requirements remain visible to the parent.

### 2. Parent-owned Bindings connect children once

Bindings describe a child's Model storage, identity, initialization, Message delivery, and OutMessage policy.

- Direct-field shorthands cover required and optional children.
- Custom readers and writers express parent policy; keyed Bindings preserve instance identity, membership, and order.
- Registered children contribute their handlers and lifecycle registrations automatically.
- Child presence and Subscription-only activation remain separate policies.

Composition derives qualified effect identities and checks child and Mount registrations, including uses through operations, initialization, nested views, and supplied content.

#### Message unions and updates contain local facts

Parents previously declared and routed child wrappers alongside their own facts:

**Before**

```ts
const Message = defineMessageUnion({
  ClickedSave: {},
  GotCounterMessage: { message: Counter.Message },
})

const update = (model: Model, message: Message) =>
  Message.match(message, {
    ClickedSave: () => ({
      model,
      commands: [SavePanel()],
    }),
    GotCounterMessage: ({ message }) =>
      foldCounter(model, message),
  })
```

**After**

```ts
const Message = defineMessageUnion({
  ClickedSave: {},
})

const update = PanelComposition.makeUpdate({
  ClickedSave: model => ({
    model,
    commands: [SavePanel()],
  }),
})
```

Your update describes your feature's behavior; Composition routes child Messages. Model, Message, and Command requirements are inferred. Parent coordination uses Binding OutMessage policies and public operations.

`PanelComposition.Message` provides the complete dispatch Schema, including generated child-routing Messages, for Runtime and DevTools.

#### Child wiring before and after

The old parent also repeated its child relationship in the fold and view:

**Before**

```ts
const foldCounter = Update.foldChild({
  update: Counter.update,
  read: (model: Model) => Option.some(model.counter),
  write: (model, nextCounter) =>
    modifyFields(model, { counter: () => nextCounter }),
  toParentMessage: message => Message.GotCounterMessage({ message }),
})

const view = Submodel.defineView<Model, Message>((model, h) =>
  h.submodel({
    slotId: 'counter',
    model: model.counter,
    view: Counter.view,
    toParentMessage: message => Message.GotCounterMessage({ message }),
  }),
)
```

**After**

```ts
const CounterBinding = PanelDefinition.makeBinding(CounterBlock, {
  field: 'counter',
})

const PanelComposition = PanelDefinition.makeComposition({
  bindings: [CounterBinding],
})

const view = PanelComposition.makeView((model, h) =>
  h.block(
    CounterBinding.embedView({
      slotId: 'counter',
      model: model.counter,
    }),
  ),
)
```

One Binding now supplies both update and view wiring.

### 3. Composition assembles child initialization

Binding policies choose child initializer arguments and which optional or keyed instances initially exist. Parent init supplies shared child-initialization context and its own fields. Composition places the child Models and collects their Commands.

Additional startup policy uses ordinary Steps. `Update.combineSteps` orders pure transitions; it does not guarantee sequential Command completion. There is no separate Runtime boot phase.

#### Initialization before and after

For example, the old Counters application initialized each child in its parent:

```ts
export const init = () => ({
  model: {
    rows: [
      { id: 'counter-0', counter: Counter.init },
      { id: 'counter-1', counter: Counter.init },
      { id: 'counter-2', counter: Counter.init },
    ],
    nextRowId: 3,
  },
})
```

The Counters Binding declares the initial instances. Parent init supplies only its own fields:

```ts
export const init = ApplicationComposition.makeInit(() => ({
  model: { nextCounterId: INITIAL_COUNTER_COUNT },
}))
```

### 4. Public child operations go through Messages

Declare a Block's public API under `operations`. Binding methods produce parent Steps that enter the child's update.

Names distinguish actions from notifications:

- `requestCloseMenu` constructs `Message.RequestedCloseMenu`.
- `informJoined` constructs `Message.InformedOfJoin`.

Parents change child state through these operations. Read-only selectors remain ordinary helpers.

#### Parent operations before and after

Search previously needed a separate adapter to close its Dialog:

**Before**

```ts
const closeDialog = Update.foldChildStep({
  update: Dialog.close,
  read: (model: Model) => Option.some(model.dialog),
  write: (model, nextDialog) =>
    modifyFields(model, { dialog: () => nextDialog }),
  toParentMessage: message => Message.GotSearchDialogMessage({ message }),
  foldOutMessage: foldSearchDialogOutMessage,
})
```

**After**

```ts
const closeDialog = DialogBinding.requestClose()
```

The Step preserves the Binding's Model mapping, Command lifting, OutMessage policy, and instance identity, and composes through `Update.combineSteps`.

### 5. Effect handlers become Layer recipes

Commands, Subscriptions, Mounts, and ManagedResources separate their contracts from handler construction.

- Attach a canonical constructor through `handler` and compose its `.layer` into `EffectsLayer`.
- Use the original definition's `.toLayer` for an external implementation.
- The root provider supplies ordinary Services. Service requirements and constructor errors remain typed through assembly.

Constructors capture stable dependencies. Shared infrastructure such as RPC clients belongs in application Service Layers; application state stays in the Model.

#### Command handlers before and after

This draft-saving Command illustrates the split. The Message constructors and `DRAFT_STORAGE_KEY` are assumed below.

**Before**

```ts
const StoreDraft = Command.define('StoreDraft', {
  args: { contents: Schema.String },
  messages: [Message.CompletedStoreDraft, Message.FailedStoreDraft],
  execute: ({ contents }) =>
    Effect.gen(function* () {
      const store = yield* KeyValueStore.KeyValueStore

      yield* store.set(DRAFT_STORAGE_KEY, contents)
      return Message.CompletedStoreDraft()
    }).pipe(
      Effect.catch(() => Effect.succeed(Message.FailedStoreDraft())),
    ),
})
```

**After**

```ts
const StoreDraft = DraftEditorDefinition.makeCommand('StoreDraft', {
  args: { contents: Schema.String },
  messages: [Message.CompletedStoreDraft, Message.FailedStoreDraft],
  handler: function* () {
    const store = yield* KeyValueStore.KeyValueStore

    return ({ contents }) =>
      store.set(DRAFT_STORAGE_KEY, contents).pipe(
        Effect.as(Message.CompletedStoreDraft()),
        Effect.catch(() => Effect.succeed(Message.FailedStoreDraft())),
      )
  },
})

const EffectsLayer = StoreDraft.layer
```

Pass `EffectsLayer` to `DraftEditorComposition.prepareBlock`, then create the completed Block with `Block.assemble(prepare)` and its checked export annotation. The handler constructor captures the storage Service when Runtime builds its Layer; each invocation receives fresh `contents`. The Program supplies storage separately:

```ts
const ApplicationLayer = BrowserKeyValueStore.layerLocalStorage

Runtime.run(program.provide(ApplicationLayer))
```

Update continues to return `StoreDraft({ contents })`.

#### Implementation dependencies stay with the handler

Consider a `CreateRoom` Command whose handler uses `RoomsClient`. Later, the handler also needs `Telemetry`.

| Boundary | Handler requirements carried directly by the Command | Handler supplied through a Layer |
| --- | --- | --- |
| Update and parent folds | Requirements change from `RoomsClient` to `RoomsClient \| Telemetry` | Continue to require the declared `CreateRoom` handler |
| Application assembly | Supplies the implementation Services | Checks the handler Layer's new `Telemetry` requirement |

Adding `Telemetry` changes the handler Layer's requirements while update keeps the same `CreateRoom` contract. Missing Services remain visible in the application's requirements.

Ordinary application execution tests should keep the real handler and replace its underlying Services. Whole-handler replacement remains available for host implementations and deliberately controlled runtime scenarios.

The cost is explicit Layer composition; it makes missing implementations and Services visible before execution.

### 6. Construction does not change operation lifetimes

| Responsibility | Lifetime |
| --- | --- |
| Application Services and handler construction | One Runtime start and its application Scope |
| Command work | Each execution, including its interruption |
| Subscription Stream | Its active registration and dependency policy |
| Mount acquisition | The mounted element |
| ManagedResource handle | Its active Model-driven acquisition Scope |

Removing an optional or keyed child stops its lifecycle work without rebuilding shared application Services. Acquisition, interruption, and cleanup retain their existing Scopes and ordering.

### 7. Guides, tooling, and testing follow the same architecture

The example apps, scaffolds, documentation, and skills demonstrate the new patterns together. Ownership lint rules help catch parent updates that bypass a child's public operations.

Story and Scene tests retain their Command-resolution workflows. Scene Subscription emission names the registered source and checks its declared result Messages. Query and KeyedQuery use the same Block and handler model.
