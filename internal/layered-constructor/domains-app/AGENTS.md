A root uses one of two complete layouts. A genuinely compact root keeps Model, Message, init, update, view, `ApplicationDefinition`, `ApplicationComposition`, `ApplicationBlock`, and any small local handler bundle together in `application.ts`. Once any root responsibility is extracted, split the whole root: retain `definition.ts` for `ApplicationDefinition` when authoring methods use it, or put a top-level `Block.makeDefinition('Application', ...).makeComposition()` chain in `composition.ts` when they do not; `model.ts`, `message.ts`, `init.ts`, `update.ts`, `view.ts`, and optional `flags.ts` own their named responsibilities; `composition.ts` owns Bindings, OutMessage folds, complete child/Mount registration, `ApplicationComposition`, and an optional `ApplicationViewBuilder`; and `block.ts` assembles `ApplicationBlock`. Even a graphless split root has `composition.ts`. Remove the emptied `application.ts` instead of using it as a forwarding barrel. A simple root `EffectsLayer` stays with its Command definitions in `command.ts`; use `layer.ts` only for substantial or reused Layer composition. Composition imports the Definition and child or Mount definitions, never root init, update, or view. Create every root with `Block.makeDefinition('Application', { Model, Message })`, author init, update, and the primary view through its Composition, then pass them explicitly to `ApplicationComposition.prepareBlock(...)` inside the private `prepare` producer. Put the adjacent `ApplicationBlock: Block.FromAssemblyWithView<typeof Model, typeof prepare> = Block.assemble(prepare)` export on the next line with no blank line. A split feature uses composition.ts, including for Mount-only registrations. Shared Mount definitions live in mount.ts. Parent-owned Bindings from `ApplicationDefinition.makeBinding(...)` are passive relationship configuration; including them in the Composition's `bindings` registers them. `entry.ts` imports `ApplicationBlock`, owns the browser container and startup inputs, creates the host with `Program.make` or `Program.makeElement`, calls `program.provide(ApplicationLayer)` when needed, and starts the Runtime. Keep root `ApplicationLayer` composition in `services.ts`. Tests and server entries import the passive Block without starting the browser Runtime. Name the root Route union `ApplicationRoute` and the root provider `ApplicationLayer` (`ApplicationTestLayer` for its test alternative).

## Project Notes

The Foldkit application root is `src/client/`, including `entry.server.ts`: server-side UI rendering belongs to the frontend application. `src/server/entry.ts` is the Worker entry; it re-exports the rendering hooks and dispatches RPC requests. Backend services live in `src/server/`; domain contracts, RPC contracts, and the candidate catalog live in `src/shared/`. Client code and backend services may import shared contracts. Shared code must not import client or server implementations. Backend services must not import client code; the Worker entry is the SSR bridge. Command and backend execution tests may connect the real client and server transports.

All root update Stories live under `src/client/story/`: `application.story.test.ts`, `progressiveDomains.story.test.ts`, and `cachedDomains.story.test.ts`. The filenames group application behaviors; every Story drives the root update. View interactions live in `src/client/scene.test.ts`. Share repeated URL handoffs and domain-result completions through `src/client/story/test.ts`; keep race-sensitive delivery ordering visible in each Story. Name tests for the trigger and observable result, and give parameterized cases distinct diagnostic names. Prefer role, label, and text locators in Scenes; use selectors for presentation structure or explicit attribute wiring. Use Scene routing configuration and explicit `Navigation.changedUrl` for typing through URL replacement, routing delivery, Clock admission, fetch completion, and displayed results. Navigation Command completion and routing delivery are separate causes. Prefer Effect `Array`, `String`, `Option`, and other data modules throughout application logic. Match literal unions exhaustively with `Match` and tagged unions with their own matcher. Use a tagged union’s named guard for one variant (`Domain.guards.Available`); reserve `isAnyOf` for multiple variants.

Name values and operations for the exact domain entity and cardinality they represent. A `DomainCandidateRange` identifies an offset/limit slice of the ordered candidate catalog; a listing may be pending or contain a checked Domain. Include units in numeric deadline and geometry names.

Import exported namespaces by name from package barrels, such as `import { Query } from 'foldkit/experimental'` and `import { Checkbox, type Listbox } from '@foldkit/ui'`, rather than using `import * as` for those namespaces.

Export a same-named decoded type beside app-owned Schemas (`export type Domain = typeof Domain.Type`) and use that name in annotations. Declare named variant aliases beside their union, such as `AvailableDomain`, when an annotation needs that precision. Derive child Model aliases once beside the completed Block, such as `ResultsListModel`. Keep Schema type extraction in these alias declarations instead of repeating it at usage sites.

Export the used Step helpers from `definition.ts` and import them by name in `update.ts` and composition policies. Export the used Definition authoring helpers alongside the Step helpers; qualify through `ApplicationDefinition` when a module works with multiple Definitions and the qualifier identifies the owner. Use `makeFieldsStep` for field-only handlers and `makeCommandsStep` for Command-only handlers; use `.fromMessage` when the producer needs only the payload. Reuse `makeStep` for mixed state-and-Command transitions, compose sequential Steps with `Update.combineSteps([...])`, and put reusable startup transitions in init's `steps` plan.

Name application Step values and factories after their operation, such as `searchQuery`, `clearSearch`, and `changeSearchQuery`. Omit the `make` prefix and `Step` suffix from application transition names. Keep framework authoring helper names such as `makeStep`, `makeFieldsStep`, and `makeCommandsStep`.

Reusable parent-owned Steps shared by update, composition, or init live in `steps.ts`. When they need subdivision, use responsibility-named files under `steps/` with an explicit `index.ts` barrel. Update maps Messages to Steps; composition registers relationships and maps child OutMessages to parent Steps. Composition imports the leaf Step module it uses. Inline OutMessage folds in their Binding policy unless the fold is reused. Keep Binding reads inside deferred producers when shared Step modules and composition depend on one another. Keep named domain types visible in useful annotations, including intermediate collections whose inferred hover expands their domain structure.

`domainsQuery.ts` owns the canonical KeyedQuery Block for `{ label, offset, limit }`. Use its bound public operations; never modify its Model internals. The root owns `selectedDomainRanges`, the ranges whose Query entries contribute to the current search view, and `searchGeneration` only for delayed planning Clock admission. Selection is application policy, not a second domain-result cache: a successful complete catalog supersedes partial ranges. Both immediate input changes and independent URL changes use the same invalidation operation; each boundary must reject work scheduled before it. `searchViewState.ts` projects status and merged domain results from Query data for the view. Its Schemas describe derived view state, not another canonical fetch state. Viewport selection plans one range at a time. A failed later range waits for explicit retry, and accepted Query completion OutMessages coordinate the next range.

Follow the pinned `query-sync` example for Route-backed state: input Messages request URL replacement; changed queries immediately invalidate and cancel pending lookups; `ChangedUrl` parses and stores the Route before starting its lookup. Pass the searched query explicitly to `searchQuery`; the URL handler passes the query from its new Route. Keep unknown paths as `NotFound` through view and server response handling. Navigation uses separate `NavigateInternal` and `LoadExternal` Commands. Use the shared `cancelSearch` to cancel pending Query windows through their Binding.

Styling follows the Foldkit website: Tailwind Vite integration, a local theme, base styles, component classes built with `@apply`, and layout utilities in view. Restrict Tailwind source detection to `src/client` so the vendored framework does not contribute utilities. Preserve the direct development stylesheet link before hydration.

Foldkit’s Vite plugin invalidates the SSR module graph during development updates. The server entry owns the development RPC handler and disposes it through `import.meta.hot.dispose` before reevaluation.

All domain availability and prices are deterministic sample data served by the same-origin Effect RPC backend. Searches must not make outbound API requests or require registrar credentials. Keep the persistent unofficial-demo label, visible sample-data labels, and demo-cart disclaimer. External Vercel links must identify their destination; the demo has no account or purchase flow. Keep the single input node and pre-hydration edits when changing search layout or startup.

`bootstrap.ts` is a native browser boundary that runs before Foldkit starts. Its listeners end at the `domains:ready` handoff. After hydration, Model, Messages, and Commands own the search. `searchLayout` distinguishes the initial landing hero from an opened search; clearing the query preserves the opened layout after keyboard dismissal. The bootstrap transfers early search activity through a temporary document marker consumed by `ReleaseEarlySearchListeners`. Keep `ReplaceSearchUrl` written with `Effect.gen`.

Use `pnpm test:e2e` for the production hydration checks. Its server port is 5180. `pnpm test:e2e:dev` checks stylesheet delivery before client scripts run on port 5181. Neither suite may reuse an existing server. The static deployment output is `dist/client`.

For a required direct child field, omit `init` when its initializer accepts no arguments; use `init: { contextToArgs }` for required inputs or `init: false` when the parent supplies that field. Optional, keyed, and accessor storage remains parent-owned when `init` is omitted; explicit `init.contextToArgs`, keyed `init.instances` / `init.toItem`, or a checked custom projection chooses automatic startup. An optional `ChildInitContext` Schema on the parent Definition contextually types selectors that prepare arguments for direct child initializers. Author root startup through `ApplicationComposition.makeInit`, returning parent-owned `model` fields plus optional ephemeral `childInitContext`, parent `commands`, and post-assembly `steps`. Composition initializes and places child Models and collects their Commands. Use an exhaustive `ApplicationComposition.makeUpdate` handler record for parent transitions; registered Bindings route generated child envelopes before local handlers. Put delivery admission in `delivery.when`, derive required child update context with `delivery.toUpdateContext`, and provide `keySchema` for a custom keyed Binding. See FOLDKIT.md for optional presence, exact keyed identity and startup Steps.

Deployment lives in `infra/alchemy.run.ts` and uses the pinned Alchemy Cloudflare Foldkit resource. Keep tooling in `infra`; the application imports no Alchemy runtime. Preserve Website/Stack names and the preview custom domain. The sample backend needs no Durable Objects or registrar secrets. Local Wrangler runs the built handler and assets with the same RPC Layer as development and production.

Domain search uses the shared `DomainsRpcs` contract over HTTP at `/rpc`, returned through `Server.Responded` in `src/server/entry.ts`. `ApplicationLayer` supplies the Runtime-scoped `DomainsClientLayer`. The Query handler returns `fetchDomains` with its Service requirement open; Foldkit supplies the handler’s captured Context when each lookup executes. Preserve typed `SearchError` failures and let interruption abort the request without producing a failure Message. Scope each RPC transport to its HTTP request. `pnpm preview` runs workerd so RPC and assets are served together. Execute the production backend Layer in tests; controlled client transport tests cover timeout and interruption. Stories and Scenes protect Model and view invariants. The Workers suite uses the real sample RPC backend, including a dedicated transport fixture on port 5183. The pinned preview needs a shared `development` build identity in Vite for coordinated client/SSR hydration.

Debounce uncached first-window lookups for 150 ms while input and pending names update immediately; progressive ranges bypass the debounce. The root Model owns `domainsQuery`, a Schema-backed KeyedQuery with one-minute freshness and `maxSettledEntries: 100`. Clock Commands report time through `CompletedReadCurrentTime`; pure Steps pass it to `requestLoadIfStale`. Fresh hits touch recency without renewing completion-based freshness and bypass debounce and RPC. Query owns retained results, pending state, and stale-response protection. Accepted completion OutMessages drive parent range planning. Do not add a second cache or copied result collection.

Domain loading is progressive: request the four Top Results first, then offset 4 and limit 56, then missing pages in the viewport and overscan area. Global price sorting or availability filtering requests the complete catalog. Derive later-page failures alongside retained domains so checked results stay usable. Failed ranges wait for explicit retry. Include label, offset, and limit in Query identity. Server RPC validates labels, ranges, JSON content, and body size, then generates sample data without external I/O.

VirtualList uses `ScrollContainer.Window()` with `rowLayout: 'Absolute'`. Keep the document as the single vertical scroll surface beneath the sticky navigation. An empty query resets the VirtualList through `initAndSet`, discarding its prior viewport and measurements while preserving Query caches. Scroll the page to the top after the empty layout commits. Its Model `scrollTop` is the signed offset from the list’s origin, so domain loading uses it directly with the measured page viewport. Preserve visible-row anchoring across responsive layouts, and keep later-page retry feedback reachable without scrolling to the catalog’s end. Arrow keys, Page Up, Page Down, and Home use the instant `ScrollPage` Command. End uses the bound VirtualList `requestScrollToEnd` operation so the final virtual row is rendered and measured before its scroll completes.

The responsive results grid uses CSS container breakpoints at 668px and 944px. `estimateResultGroupHeightPx` supplies matching VirtualList estimates and progressive domain-planning geometry; dynamic measurements handle wrapped names and prices. The pinned UI package uses a tracked pnpm patch to order changed-width measurements before scroll observations, preserving the pre-reflow anchor across responsive layouts. Native scroll observations with an older row-layout version use their observed anchor when the scroll offset changed; resize observations at the measured offset preserve the pre-reflow anchor. When an external viewport starts above the list, the patch preserves its signed offset rather than anchoring a row that may move during filtering or sorting. Preserve the browser resize-anchor and sort-position assertions when upgrading the dependency.

Desktop filters use typed `@foldkit/ui` Listbox Blocks. The mobile filter Dialog exposes direct choices with selected checkmarks and closes after selection. Its enter and leave motion uses the Dialog Animation lifecycle and respects reduced motion. The parent owns selected values; share filter transitions through `steps/filters.ts`. Keep selected text in Listbox trigger accessible names, and anchor popup panels inside the main landmark.

The root Model owns one `cart`. Its Cart Schema lives under `src/client/domain/`; sample prices cannot represent a purchase or reservation. Cart admission remains idempotent because repeated clicks may arrive before rendering updates the control. All current availability, pricing, and cart behavior are simulated.

Keep pure client domain Schemas and operations under `src/client/domain/`, with explicit barrel exports. Export the cart Schema module as `Cart` and name the root field `cart`. Keep `model.ts` limited to the root Model Schema and decoded type.

Prefer value-first `pipe(value, operation, nextOperation)` for transformation chains, including `pipe(record, Record.get(key), Option.getOrElse(...))`, instead of nesting the first operation or calling `.pipe` on its result.

Focus Commands use `Dom.focus` with `preventScroll: true`. Share target IDs between view and Commands through `focusTarget.ts`; use a dedicated ID for a specific control instead of a CSS structure selector.
