## Non-blocking hardening observation

### Development cleanup when Vite HMR is disabled

**Confidence:** High

When development HMR is disabled, module-level application resources cannot receive Vite’s normal dispose callback. Repeated edits can therefore retain old handlers or listeners until the development process is restarted. The limitation is explicitly documented in [ssr.ts](/private/tmp/foldkit-daybreak-50d8e5f375-20261106/source/packages/vite-plugin/src/ssr.ts:933).

- **Preconditions:** Development server, HMR disabled, and an entry module that acquires persistent resources.
- **Impact:** Development-only duplicate handlers or leaked resources; no demonstrated production or remote privilege boundary.
- **Smallest improvement:** Add a plugin-owned disposal route independent of module HMR, or make restart-on-edit mandatory and mechanically enforced for this mode.
- **Focused check:** Run an HMR-disabled development fixture with a counted scoped listener, trigger multiple rebuilds, and assert that at most one live listener remains or that the process is deliberately restarted.

This does not justify blocking the preview on security grounds.

## Inherited risks

These were not introduced or materially worsened by the candidate:

- **Explicit fixed-port DevTools/MCP mode:** `devToolsMcpPort` binds a predictable, unauthenticated WebSocket listener and does not enforce an Origin allowlist. A browser page or network peer able to reach that listener may access DevTools capabilities. The safer automatic relay instead uses loopback, an ephemeral port, a high-entropy token, challenge/HMAC proof, and ownership-checked registry records. Fixed-port mode remains an explicitly selected development exposure.
- **Relay registry race surface:** The current candidate validates scheme, credentials, host, port, path, and token before performing a liveness probe in [relayRegistry.ts](/private/tmp/foldkit-daybreak-50d8e5f375-20261106/source/packages/devtools-mcp/src/relayRegistry.ts:48). This addresses the earlier ordering concern; ordinary filesystem race limitations remain.
- **Dependency advisories:** The recorded checkpoint contains two moderate build-tool advisories involving `glob` and `minimatch`; it is not a clean or universally patched dependency tree. The recorded reachability is build cleanup and fixed repository/CI tooling rather than production request processing. See [dependency-advisories/README.md](/private/tmp/foldkit-daybreak-50d8e5f375-20261106/source/internal/layered-constructor/dependency-advisories/README.md:1). This review was not a fresh advisory audit.
- **Release bootstrap:** The release workflow downloads the pinned npm CLI tarball without independently pinning and checking its digest before extraction. TLS and registry integrity remain trusted at that bootstrap step. A pinned SHA-512 verification would reduce this inherited supply-chain exposure.
